# Размещение статической сборки

Соберите `npm run build` и разместите содержимое `dist/` на статическом сервере. Перед сборкой задайте нужные публичные переменные окружения. Для загрузки моделей нужен запущенный backend и перенаправление `/api/` на него.

## Пример Nginx для корня домена

```nginx
server {
    listen 80;
    server_name printlab.example.com;
    root /var/www/printlab/dist;
    index index.html;

    location /api/ {
        client_max_body_size 16m;
        proxy_pass http://127.0.0.1:8080;
        proxy_read_timeout 200s;
    }

    location /assets/ {
        try_files $uri =404;
        add_header Cache-Control "public, max-age=31536000, immutable";
    }

    location = /index.html {
        add_header Cache-Control "no-cache";
    }

    location / {
        try_files $uri $uri/ /index.html;
    }
}
```

Это пример для закрытого тестового окружения. Для публичного запуска используйте инструкцию `docs/server-launch.md` и шаблоны `deploy/` из репозитория **printlab-backend**: HTTPS, отдельную службу API, ограничения ресурсов слайсера и разрешение только трёх нужных API-маршрутов. Общий прокси `/api/` из примера выше открывает также служебные методы бэка и не подходит для публичного сервера. Публичный Linux-запуск требует отдельной проверки настоящего Bambu Studio.

Правило `/api/` сохраняет префикс при передаче на backend и исключает SPA fallback. Лимит запроса учитывает multipart-обёртку; лимит самого STL на backend — 15 МиБ. Vite proxy применяется только при локальном запуске и preview. На сервере размещается готовый `dist`, процесс Vite не запускается. Telegram-бот работает отдельной службой и использует общий API; его токен никогда не задаётся в `VITE_*`.

Файлы `/assets/` имеют хеши и могут кэшироваться надолго. `index.html` должен перепроверяться, чтобы браузер получал ссылки на новую сборку. Отсутствующий ресурс в `/assets/` возвращает 404. Неизвестный маршрут приложения возвращает оболочку SPA с HTTP 200, затем React показывает страницу «не найдено».

## Подкаталог

Для размещения по `/printlab/`:

```sh
npm run build -- --base=/printlab/
```

Разместите файлы под этим URL. В статическом сервере fallback должен вести на `/printlab/index.html`, а правило ресурсов — на `/printlab/assets/`. Базовый путь маршрутизатора берётся из сборки.

Проверьте главную, прямую ссылку на вложенный маршрут, перезагрузку страницы и загрузку ресурсов. `npm run preview -- --base=/printlab/` позволяет проверить такой вариант локально.

## Docker и автоматическое обновление

`Dockerfile` упаковывает проверенный `dist` в Nginx без root. Браузер продолжает
обращаться к `/api` на том же HTTPS-адресе. Внешний Nginx сервера направляет
API в backend, а страницы и файлы — в frontend-контейнер на `127.0.0.1:8081`.
Настройки API, сертификаты и SSH-ключи в образ фронта не включаются.

Workflow `CI and deploy` запускает проверки и Playwright для PR и `main`.
После успешного push в `main` публикует GHCR-образ по SHA, а сервер получает его
по digest. Environment `production` должен разрешать только `main` и содержать
`DEPLOY_SSH_KEY` с отдельным ограниченным ключом именно фронта. Сам workflow
без этой однократной настройки автодеплой не включает.

Сервер обновляет только frontend, проверяет healthcheck и главную страницу;
при ошибке возвращает предыдущий образ. Backend пересоздавать не требуется.
Общая серверная блокировка предотвращает пересечение деплоев из двух репозиториев.
Подробная установка, ограничения и откат: `printlab-backend/docs/container-deployment.md`.
